### Login screen — real, working, and reasonably careful
`app/login.tsx` calls `useAuth().signIn()` (client-side email/password format validation only);
the actual gating logic lives in `lib/AuthContext.tsx`. Confirmed:
- Uses real **Supabase Auth** (`supabase.auth.signInWithPassword`).
- Rejects any role other than `site_engineer` — **and separately** rejects an inactive account,
  checking **two different fields** (`status !== 'active'` OR `is_active === false`):
```ts
async function loadSiteEngineerProfile(email: string): Promise<ProfileLookup> {
  const { data, error, status } = await supabase
    .from('user_profiles')
    .select('id, email, full_name, role, status, is_active')
    .eq('email', email)
    .maybeSingle();

  if (error) {
    const rlsBlocked = status === 401 || status === 403 || error.code === '42501';
    return { ok: false, rlsBlocked, message: rlsBlocked
        ? 'user_profiles is not readable by the logged-in client — likely missing a grant/RLS policy.'
        : error.message };
  }
  if (!data) return { ok: false, rlsBlocked: false, message: "Your account isn't set up for this app yet. Contact your admin." };
  if (data.role !== 'site_engineer') return { ok: false, rlsBlocked: false, message: 'This app is for site engineers only. Use the web portal instead.' };
  if (data.status !== 'active' || data.is_active === false) return { ok: false, rlsBlocked: false, message: 'Your account is currently inactive. Contact your admin.' };

  return { ok: true, profile: { id: data.id, email: data.email, fullName: data.full_name, role: data.role } };
}
```
- This check re-runs **on every app relaunch** (`restore()`, via `supabase.auth.getSession()`), not
  just at initial login — a locally-persisted session doesn't outlive an admin deactivating the
  account server-side, though an *already-open* session isn't force-killed mid-use.
- **A real, present risk worth flagging plainly**: the login form's email/password fields are
  pre-filled with a hardcoded demo credential (`siteengineer.demo@gmail.com` / `Engineer#2026`),
  with an in-code `// TODO: clear these defaults before any real release/handoff build.` This is a
  live credential sitting in plaintext source right now, not a hypothetical.

### Offline sync foundation — real, three-part system, working end-to-end

**Local queue (`lib/db/localDb.ts`, `expo-sqlite`)** — one table:
```sql
CREATE TABLE IF NOT EXISTS sync_queue (
  id TEXT PRIMARY KEY,
  entity_type TEXT NOT NULL,
  payload TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',
  retry_count INTEGER NOT NULL DEFAULT 0,
  last_error TEXT,
  created_at TEXT NOT NULL,
  synced_at TEXT
);
```
`status` ∈ `pending | syncing | synced | failed`. `payload` is a raw JSON string. `id` is a locally
generated string (`${Date.now()}-${random}`), not a UUID library. Functions: `enqueue`,
`getPending`, `getEntriesByType` (used to derive local UI state without a network round-trip),
`markSyncing`/`markSynced`/`markRetry`/`markFailed`, `getQueueCounts`. Every mutation fires a tiny
pub/sub (`lib/sync/syncEvents.ts`) so UI queue-count badges update live.

**Sync engine (`lib/sync/syncEngine.ts`)** — `processQueue()` is guarded against overlapping runs
(an `isProcessing` flag plus a `rerunRequested` flag, so a trigger arriving mid-run loops again
instead of dropping a row) and processes pending rows **strictly sequentially**, not in parallel,
with a 200ms pause between rows. Retry backoff: exponential, `1000ms * 2^retryCount` capped at
30s, tracked in an **in-memory-only** `Map` (deliberately not persisted — a restart resets the
cooldown, which the code comments say is intentional: it only needs to stop one live session from
hammering a row, not survive a restart). After 5 failed attempts, or immediately if no handler is
registered for a row's `entity_type`, the row is marked permanently `failed`.

**Triggers (`lib/sync/syncTriggers.ts`)** — event-driven, no polling: fires on the
offline→online `NetInfo` transition, on app-foreground (`AppState`), and once at startup
(`app/_layout.tsx`'s `useEffect` calling `startSyncTriggers()`) to catch anything queued from a
previous session.

**`entity_type` routing (`lib/sync/handlers.ts`)** — the generalization mechanism for future
feature types:
```ts
export const syncHandlers: Record<string, SyncHandler> = {
  test_entry: syncTestEntry,
  attendance: syncAttendance,
};
```
The queue table and engine have no knowledge of what entities exist — that's entirely in this map.
Adding a real future feature (e.g. `dpr`) means adding one more key here and calling
`enqueue('dpr', payload)` from a new screen; the engine itself never changes. This is stated
explicitly in the file's own comment.

**Current test entity (`test_entry`)** — `app/(authenticated)/sync-test.tsx` is an explicitly
labeled **THROWAWAY** 3-field form, meant to be deleted (along with its handler and its disposable
`test_sync_entries` Supabase table) once a real feature is wired into the same queue instead.
Submitting it calls `enqueue('test_entry', {...})` — queued only, no immediate sync attempt.

### Attendance / GPS check-in screen — **real and functional, not a placeholder**
This is the one genuinely functional feature beyond auth+sync plumbing. `app/(authenticated)/attendance.tsx`:
- Fetches real projects from Supabase (`lib/attendance/projects.ts`), auto-selects if there's
  exactly one, otherwise shows a picker.
- Requests foreground location permission, gets a high-accuracy GPS fix
  (`Location.getCurrentPositionAsync({ accuracy: Location.LocationAccuracy.High })`), computes
  distance from the selected project's site coordinates via a real haversine implementation
  (`lib/location/haversine.ts`).
- Reads Android's `location.mocked` flag (see §5 for what "verified" actually means here) and
  builds a flags object (`lib/attendance/flags.ts`) covering: no site location configured, outside
  a 300m radius, suspected mock location, and (finalized at actual submit time, not capture time)
  an implausible >5-minute gap for a claimed-"immediate" send.
- Determines CHECK_IN vs. CHECK_OUT from **local device history only**
  (`getEntriesByType('attendance')`, today's most recent local entry) — not a server query. This is
  a known, documented simplification: it's per-device and has no idea about a check-in made from a
  different phone.
- Submits via `enqueueAndSync('attendance', payload)` — an immediate best-effort sync attempt
  (unlike the test screen, which only queues).
- The `attendance` sync handler writes to a table called `attendance_records` — columns match the
  `AttendanceRecord` model in the sibling `admin-web` repo's Prisma schema (confirmed independently
  from that repo's side, not from inside this one — this repo has no schema/migration files of its
  own to check against). `submissionMode` is local-only bookkeeping and is **not** sent to
  Supabase.
- Handles denied permission gracefully (an "Open Settings" deep link if re-prompting isn't
  possible), and shows a "checked in/out at HH:MM" result with a "noted for review" note when
  flagged.

## 3. Architecture

### Expo Router structure (full tree under `app/`)
```
app/
├── _layout.tsx                     — root Stack layout: wraps AuthProvider, starts sync triggers
├── index.tsx                       — bare redirect to /login
├── login.tsx                       — login screen
└── (authenticated)/
    ├── _layout.tsx                 — Drawer layout, auth-gated
    ├── home.tsx                    — placeholder
    ├── attendance.tsx              — real GPS check-in/out screen
    └── sync-test.tsx               — throwaway sync-queue test screen
```
`typedRoutes` experiment is on; deep-link scheme is `mobileportal`.

### Supabase client setup (`lib/supabase.ts`, full file)
```ts
import 'react-native-url-polyfill/auto';
import AsyncStorage from '@react-native-async-storage/async-storage';
import { createClient } from '@supabase/supabase-js';
import { AppState } from 'react-native';

const supabaseUrl = process.env.EXPO_PUBLIC_SUPABASE_URL!;
const supabaseAnonKey = process.env.EXPO_PUBLIC_SUPABASE_ANON_KEY!;

export const supabase = createClient(supabaseUrl, supabaseAnonKey, {
  auth: { storage: AsyncStorage, autoRefreshToken: true, persistSession: true, detectSessionInUrl: false },
});

AppState.addEventListener('change', (state) => {
  if (state === 'active') supabase.auth.startAutoRefresh();
  else supabase.auth.stopAutoRefresh();
});
```
Confirmed: **AsyncStorage is used for auth session persistence** (`@react-native-async-storage/async-storage@2.2.0`).
This client is a module-level singleton created at import time — worth knowing that a blank env
var throws synchronously here (this was reportedly the root cause of an earlier crash).

### Local SQLite queue design
See §1 for the full schema and behavior. Architecturally, the key property is that the **queue
table and sync engine are entity-agnostic** — `entity_type` (free string) + `payload` (JSON string)
means the SQLite schema never needs to change to support a new feature; only `lib/sync/handlers.ts`'s
map needs a new entry, and a new screen needs to call `enqueue()`/`enqueueAndSync()`. Retry counts
are persisted (survive a restart); backoff cooldown timing is not (intentionally — see §1).

## 5. Known Risks / Open Items

### RLS on `user_profiles` — **status unverified from this repo**
No SQL, migration, or RLS policy definition file exists anywhere in this repo (confirmed: zero
`*.sql` or `*migration*` files outside `node_modules`). What exists is defensive client-side
handling that distinguishes an RLS-blocked read from "no row"/"wrong role"
(`rlsBlocked = status === 401 || status === 403 || error.code === '42501'`, logged via
`console.warn` if hit) — but that's just detection code, not proof of the actual database-side
policy state. `CHANGELOG.md` claims a live test against the real Supabase project (anon key only)
returned `200 OK` with real, unredacted `user_profiles` rows — i.e., claims RLS is effectively wide
open on that table today, with `user_profiles.id` being an independently-generated UUID (not a FK
to `auth.users.id`), meaning any future restrictive policy would need to key off
`email = auth.email()`, not `id = auth.uid()`. **This could not be independently re-confirmed while
writing this document** — no network access to the live project, and no local schema file to check
against. Treat this as **unverified and worth a direct live check**, not settled fact — this is
exactly the kind of gap the original request asked to be honest about rather than papered over.

### Android mock-location handling — implemented and wired, but **not evidenced as device-tested**
- `expo-location@57.0.2` is installed (confirmed against the actual resolved `node_modules`
  version, not just the `package.json` range).
- The `mocked?: boolean` field is real, Android-only, per the library's own type declarations:
```ts
/**
 * Whether the location coordinates is mocked or not.
 * @platform android
 */
mocked?: boolean;
```
- This **is** genuinely wired into the app, not aspirational — `attendance.tsx` reads
  `Platform.OS === 'android' ? !!location.mocked : false` and threads it through to
  `mockLocationSuspected` on the actual attendance-record insert. On iOS it's permanently
  hardcoded to `false`, correctly documented as a real platform limitation (no public Apple API for
  third-party mock-location detection), not a bug.
- What's **not** evidenced anywhere in this repo: an actual test run against a real physical
  Android device with a mock-location app installed, confirming `location.mocked` actually flips to
  `true` in practice. Confirming the type/API exists (done above) is not the same as confirming
  real-device behavior was ever exercised — there's no test harness or recorded test run anywhere
  in this codebase proving that. Flag this as unverified, not confirmed working end-to-end on
  hardware.
